My portfolio's production build was broken and I did not know, because the
command I ran every day was not the command that checks.

## The change

In Next 15, `params` and `searchParams` in a page are Promises. The old shape:

```tsx
export default function Page({ params }: { params: { slug: string } }) {
  return <h1>{params.slug}</h1>;
}
```

becomes:

```tsx
export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  return <h1>{slug}</h1>;
}
```

This is not cosmetic. Making params async is what lets Next start rendering the
static shell of a route before it knows the dynamic values.

## Why it kept working anyway

Next 15 ships a compatibility layer. The object handed to your component is a
Promise that also answers synchronous property access, logging a deprecation
warning when you use it that way. So `params.slug` still returns the slug, your
pages still render, and nothing looks wrong in the browser.

That shim is temporary. When it goes, code relying on it stops working, and by
then you may have written a great deal of it.

## Why the type error was invisible

This is the part that caught me.

Next generates route types into `.next/types` during a build and checks your
pages against them. Mine failed that check:

```
Type '{ params: { slug: string; }; }' does not satisfy the constraint 'PageProps'.
  Types of property 'params' are incompatible.
    Type '{ slug: string; }' is missing the following properties
    from type 'Promise<any>': then, catch, finally
```

I never saw it, for two compounding reasons:

- `tsc --noEmit` passes. Those generated route types only exist *after* a
  build, so a standalone type-check has nothing to compare against.
- My build script was `next build --turbopack`, and the Turbopack builder skips
  that validation entirely.

The one command that would have caught it was the one I had optimised away for
speed.

```json
{
  "scripts": {
    "dev": "next dev --turbopack",
    "build": "next build",
    "typecheck": "tsc --noEmit"
  }
}
```

Turbopack in `dev` is a straight win. In `build`, on a project where the build
takes seconds anyway, trading a correctness check for speed is a bad deal.

## What I would check in your project

Three commands, in order:

```bash
npx tsc --noEmit
npx next build
npm audit
```

Note the missing `--turbopack` on the second. If it fails while the first
passes, you have the same problem. The fix is mechanical, and the type error
names the exact files.

## The general shape of this bug

The failure was not the API change. Async params are documented and the
migration is trivial.

The failure was that my toolchain had three ways to check correctness, and I
had arranged for the fastest one to run and the thorough one not to. Every
green check I saw was technically honest and collectively meaningless.

Worth asking of your own setup: when CI says pass, which checks actually ran?
